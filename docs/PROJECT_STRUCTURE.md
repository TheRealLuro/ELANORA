# Project structure

Every folder, what lives in it, and why it is separate from the others.

## Dependency graph

Modules depend only on those above them. This is enforced by the CMake target
graph, not by convention.

```
common                      types, CSV, UI shell — depended on by everything
  ├── device                Muse 2 I/O                   → common
  │     └── collector       stimulus + protocol          → common, device
  │           └── server    HTTP host + round storage    → common, collector
  ├── data                  features + statistics        → common
  │     └── models          regression + optimizer       → common, data
  └── web                   phone collector              (no C++ dependency)
```

`models` depending on `data` is deliberate: the evidence gate lives in `data/`
because it is data analysis, and the optimizer must be able to refuse a goal
whose outcome has no statistical support.

## Modules

Each C++ module follows the same shape:

```
<module>/
  CMakeLists.txt
  include/elanora/<module>/   public headers
  src/                        implementation
  tests/                      Catch2 tests
  app/                        executables, where the module ships one
```

### `common/`
Shared vocabulary. `types.hpp` defines the enums every layer agrees on
(`Period`, `Condition`, `SensorId`, `Band`), `csv.hpp` the reader and writer,
`theme.hpp` and `render.hpp` the UI primitives, `ui_shell.hpp` the GLFW/ImGui
window.

### `device/`
Muse 2 acquisition over BrainFlow. `muse_device.hpp` wraps `BoardShim` so no
exception reaches the UI thread and no channel index is ever hardcoded;
`stream_recorder.hpp` holds ring buffers per preset; `signal_quality.hpp`
scores an electrode.

Ships `muse_monitor` (live dashboard, numeric and waveform views) and
`muse_probe` (prints what BrainFlow reports for the board, without connecting).

> Formerly named `LSL/`. It contains no Lab Streaming Layer and never did.

### `collector/`
The experiment itself, with no I/O attached. `session.hpp` holds the protocol
constants, the frequency set, the round schedule and the trial state machine;
`tone.hpp` generates the stimulus; `schema.hpp` declares the dataset columns.

Deliberately free of ImGui and BrainFlow so the experimental rules are testable
headless. `view.cpp` (UI) and `recorder.cpp` (disk) are separate targets for
that reason.

### `data/`
Everything between raw samples and a verdict. Band power, heart features,
breathing features, per-signal quality control, the dataset builder, the
statistics primitives, and `evidence.hpp` — the gate that decides whether any
of it survives scrutiny.

Ships `elanora_data`: browse recordings, inspect features, read the evidence.

### `models/`
Ridge and Gaussian Process regression, the model ladder that picks the simplest
adequate model, grouped cross-validation, the registry of 22 single-output
regressors behind the 6 logical models, forward prediction and the inverse
optimizer.

Ships `elanora_models`: train, predict, invert.

### `server/`
`elanora_serve` — hosts the phone collector, hands out the round schedule
generated by the C++ `build_schedule()`, and writes uploaded rounds into the
dataset. Validates before writing: a malformed upload is rejected rather than
stored as something that later reads wrong.

### `web/`
The phone collector. Plain ES modules, no build step, no npm.

| File | Role |
|---|---|
| `muse.js` | Web Bluetooth connect, GATT resolve |
| `decode.js` | Packet decode — EEG, PPG, IMU, telemetry |
| `ringbuffer.js` | Sequence-derived timebase with NaN gap fill |
| `dsp.js` | Display-only quality, band power, heart, breathing, motion |
| `tone.js` | Stimulus rendering — a port of `tone.cpp` |
| `protocol.js` | Round phase state machine |
| `upload.js` | CSV assembly, durable upload queue |
| `collector.js` | Session runner |
| `app.js` | Screen router and wiring |
| `index.html` | Monitor and collector |
| `data.html` | Collection status, read on the PC |
| `probe.html` | Is Web Bluetooth available in this browser |
| `inspect.html` | Raw packet inspector, for verifying the decode |
| `tests.html` | 90 tests, run in the browser |

### `tools/`
Developer tools, not part of the shipped system.

- `tone_reference` — emits reference values from the C++ stimulus generator so
  the browser port can be checked against it numerically. Run after any change
  to `tone.cpp`; the JavaScript conformance test then fails if they drift.
- `ui_smoke` — opens a window and closes cleanly, proving the UI shell works
  without a headset.

## Data

```
data/datasets/
  subjects.csv   sessions.csv   trials.csv   surveys.csv
  raw/<session_id>/<trial_id>_{eeg,ppg,imu,markers}.csv
  features/      brain, heart and breath features per period
  ml/            wide per-trial rows the models consume
  analysis/      evidence.csv — the 22-outcome verdict table
```

**Raw recordings are never overwritten and never committed.** Everything under
`raw/`, `features/`, `ml/` and `analysis/` is gitignored: the raw files are the
only irreplaceable artifact, and everything downstream is regenerable from
them.

The column layout lives in exactly one place,
`collector/include/elanora/collector/schema.hpp`, because two writers produce
these files — the desktop recorder and the upload server — and two copies of a
schema drift until something reads one of them wrong.

| `elanora_models` | Train, predict, invert |
| `tone_reference` | Conformance fixture generator (dev) |
| `ui_smoke` | UI shell smoke test (dev) |

## Tests

| Suite | Count | Run with |
|---|---|---|
| C++ (Catch2) | 260 | `ctest --test-dir build -C Release` |
| JavaScript | 90 | open `/tests.html` in a browser |

The JavaScript suite includes a numerical conformance check: the browser
stimulus generator is asserted against reference values emitted by the C++ one,
to 1e-6 on RMS and on eight waveform probes. The phone makes the sound, so a
port that drifted would change the experiment without changing anything
visible.
